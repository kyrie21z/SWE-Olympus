# 库存与订单预占系统测试需求

本系统用于管理少量商品的可用、预占和已成交库存，重点验证库存守恒、订单状态流转、重复请求和并发竞争。交付范围为一个可测试的 Python 业务核心及其自动化测试，适合用 SWE-Olympus 检查需求到设计、任务规划、受控执行及验收的衔接。

需求编号：REQ-INVENTORY-RESERVATION。版本：1。日期：2026年11月18日。来源及确认均为构造测试数据，不代表真实用户签认。配套 `requirement.json` 是本版本可导入的结构化需求；本文件提供规则说明、示例及验收用例。

## 一 业务范围和术语

商品以 `sku` 标识，订单以 `order_id` 标识。每个订单只预占一个商品的一定数量；订单编号在同一服务实例内跨商品唯一。所有调用方拥有相同业务能力，本期不引入用户身份或权限系统。

库存字段定义如下。`initial` 为创建时的库存，创建后保持不变；`available` 为可被新订单占用的数量；`reserved` 为全部 RESERVED 订单的数量之和；`sold` 为全部 CONFIRMED 订单的数量之和。CANCELLED 订单不占库存，但保留查询记录及订单编号。

任何可见状态均须满足 `initial = available + reserved + sold`，且各字段为非负整数。每个服务实例从空状态开始，不同实例及不同商品的数据相互隔离。

## 二 功能需求和验收条件

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| FR-001 | 创建商品及初始库存；商品编号唯一，库存创建后不得直接修改。 | 首次创建返回 initial=available=指定库存、reserved=sold=0；同编号再次创建返回 SKU_EXISTS，原记录不变。 |
| FR-002 | 使用订单编号为单个商品预占指定数量；预占必须原子完成。 | 新订单预占成功后状态 RESERVED，available 减少 quantity，reserved 增加 quantity；未知商品返回 SKU_NOT_FOUND，库存不足返回 INSUFFICIENT_STOCK，不创建订单。 |
| FR-003 | 确认预占订单，将其转为已成交状态。 | RESERVED 确认后变为 CONFIRMED，reserved 减少 quantity、sold 增加 quantity、available 不变；CANCELLED 确认返回 STATE_CONFLICT。 |
| FR-004 | 取消预占订单并归还库存。 | RESERVED 取消后变为 CANCELLED，reserved 减少 quantity、available 增加 quantity、sold 不变；CONFIRMED 取消返回 STATE_CONFLICT。 |
| FR-005 | 预占以全局唯一订单编号实现幂等；失败请求不占用订单编号。 | 同订单编号且商品和数量相同的重复预占返回当前订单，所有状态下均不再次扣库存；任一参数不同返回 ORDER_CONFLICT；首次失败后可修正参数并复用编号。 |
| FR-006 | 确认和取消的重复请求保持终态幂等。 | 重复确认 CONFIRMED、重复取消 CANCELLED 均成功并返回原订单；未知订单返回 ORDER_NOT_FOUND；终态不复活，库存不再次变化。 |
| FR-007 | 查询商品库存及订单详情，返回固定字段。 | 商品返回 sku、initial、available、reserved、sold；订单返回 order_id、sku、quantity、state；未知商品或订单分别返回 SKU_NOT_FOUND 或 ORDER_NOT_FOUND。 |
| FR-008 | 严格校验编号及数量，不进行隐式转换。 | 编号须为匹配 [A-Za-z0-9_-]{1,32} 的字符串，区分大小写且不去空格；初始库存为0至10000的整数，预占数量为1至10000的整数；拒绝布尔值、浮点数、数字字符串，返回 INVALID_ARGUMENT。 |
| FR-009 | 并发预占、确认、取消及查询必须保持库存守恒和合法状态。 | 所有可见快照均满足 initial=available+reserved+sold 且三项非负；100个不同订单并发预占10件库存时恰好10个成功；同订单确认与取消竞态仅一个终态成功，另一个返回 STATE_CONFLICT。 |
| FR-010 | 查询和写操作返回独立快照，调用方不得通过返回值修改内部状态。 | 返回 data 为普通字典；修改返回字典中的字段后再次查询，内部库存及订单状态不变；各商品与不同服务实例互不影响。 |
| FR-011 | 统一返回结果和失败语义；失败不得改变库存或订单。 | 成功返回 {ok:true,data:对象}，失败返回 {ok:false,error:{code:错误码}}；校验顺序为参数格式、订单冲突、商品存在、库存充足；业务错误不抛异常，失败自身不修改状态，无并发写时前后快照相同。 |
| NFR-001 | 交付 Python 3.12及以上可运行的单进程内存业务核心。 | 提供 InventoryService 的 create_sku、reserve、confirm、cancel、get_sku、get_order 六个公开方法；运行核心无需第三方包、数据库或网络，不跨进程共享状态。 |
| NFR-002 | 交付可重复执行的自动化测试及中文运行说明。 | 使用 unittest 覆盖正常、边界、非法状态、幂等、数据隔离和并发；100请求抢10件测试用全新实例连续执行5轮均通过；报告实际测试数和结果。 |

## 三 输入和返回约定

公开入口为 `InventoryService()` 创建的服务实例。各方法均返回字典，不通过打印输出传递业务结果。

| 方法 | 参数 | 成功时的 data |
| --- | --- | --- |
| create_sku | sku, initial_stock | 商品快照 |
| reserve | order_id, sku, quantity | 订单快照 |
| confirm | order_id | 订单快照 |
| cancel | order_id | 订单快照 |
| get_sku | sku | 商品快照 |
| get_order | order_id | 订单快照 |

成功结果的完整结构为 `{"ok": true, "data": {...}}`；失败结果为 `{"ok": false, "error": {"code": "错误码"}}`。`ok` 使用布尔值。业务校验失败不抛出异常；方法参数个数错误等 Python 调用错误不在业务错误约定中。返回的 `data` 是可修改的独立普通字典。

编号须整串匹配 `[A-Za-z0-9_-]{1,32}`。例如 `SKU-A`、`ORD_001` 有效，空串、中文、含空格或斜杠、33个字符的编号无效。`sku-a` 与 `SKU-A` 是不同编号。初始库存允许0和10000；预占数量允许1和10000。`True`、`1.0`、`"1"`、`None` 均不能作为数量。

按下列顺序返回第一个业务错误：

1. 检查当前方法所有参数的格式、类型和取值范围，失败返回 `INVALID_ARGUMENT`。
2. 创建商品时检查重复编号，返回 `SKU_EXISTS`；预占时先检查已有订单，参数相同直接返回原订单，参数不同返回 `ORDER_CONFLICT`；其余订单方法先检查订单存在性，失败返回 `ORDER_NOT_FOUND`。
3. 新订单预占检查商品存在性，失败返回 `SKU_NOT_FOUND`；商品查询也使用该错误码。
4. 新订单预占检查可用库存，失败返回 `INSUFFICIENT_STOCK`；确认和取消检查状态，失败返回 `STATE_CONFLICT`。

失败预占不保存订单，因此库存不足后可使用同一编号改为较小数量重试。已有订单无论处于何种状态，都不允许更换商品或数量；已取消订单的原参数重复预占返回 CANCELLED，不产生新预占。

## 四 订单状态和库存变化

| 当前状态 | 操作 | 结果状态 | 库存变化 |
| --- | --- | --- | --- |
| 不存在 | 预占成功 | RESERVED | available 减 quantity，reserved 加 quantity |
| RESERVED | 确认 | CONFIRMED | reserved 减 quantity，sold 加 quantity |
| RESERVED | 取消 | CANCELLED | reserved 减 quantity，available 加 quantity |
| CONFIRMED | 重复确认 | CONFIRMED | 无变化，成功 |
| CANCELLED | 重复取消 | CANCELLED | 无变化，成功 |
| CONFIRMED | 取消 | CONFIRMED | 无变化，STATE_CONFLICT |
| CANCELLED | 确认 | CANCELLED | 无变化，STATE_CONFLICT |
| 任一已有状态 | 原参数重复预占 | 原状态 | 无变化，成功 |

所有检查和状态更新须对并发调用原子生效，查询也须得到一致快照。同一个 RESERVED 订单被一个确认请求和一个取消请求同时操作时，最终只能为 CONFIRMED 或 CANCELLED；恰好一个请求成功，另一个返回 STATE_CONFLICT。成功的终态决定库存归属。

## 五 基准业务走查

下列步骤在同一个新实例中顺序执行。库存列顺序为 available、reserved、sold；每一步 initial 均为3。

| 步骤 | 调用 | 预期结果 | 库存 |
| --- | --- | --- | --- |
| 1 | create_sku("SKU-A", 3) | 创建成功 | 3, 0, 0 |
| 2 | reserve("ORD-1", "SKU-A", 2) | ORD-1 为 RESERVED | 1, 2, 0 |
| 3 | 重复步骤2 | 返回原订单，不重复占用 | 1, 2, 0 |
| 4 | reserve("ORD-2", "SKU-A", 2) | INSUFFICIENT_STOCK，ORD-2 不存在 | 1, 2, 0 |
| 5 | cancel("ORD-1") | ORD-1 为 CANCELLED | 3, 0, 0 |
| 6 | reserve("ORD-2", "SKU-A", 2) | ORD-2 为 RESERVED | 1, 2, 0 |
| 7 | confirm("ORD-2") | ORD-2 为 CONFIRMED | 1, 0, 2 |
| 8 | 重复步骤7 | 返回原订单，不重复成交 | 1, 0, 2 |
| 9 | cancel("ORD-2") | STATE_CONFLICT | 1, 0, 2 |
| 10 | reserve("ORD-1", "SKU-A", 2) | 返回旧 CANCELLED 订单 | 1, 0, 2 |

## 六 验收用例

每个用例使用独立实例，除非步骤明确要求复用。除显式验证某个中间步骤外，均在用例结束时检查库存守恒。下列是待执行的验收定义，不是已通过的结果。

| 用例 | 对应需求 | 操作和明确断言 |
| --- | --- | --- |
| TC-01 | FR-001 | 创建库存0和10000的两个商品，核对全部库存字段；重复创建已有商品返回 SKU_EXISTS，原库存不变。 |
| TC-02 | FR-002 | 库存3预占2，库存变为1,2,0；订单字段及 RESERVED 状态正确。 |
| TC-03 | FR-003 | 确认 TC-02 的订单，库存变为1,0,2，订单变为 CONFIRMED。 |
| TC-04 | FR-004 | 库存3预占2后取消，库存恢复3,0,0；取消记录仍可查询。 |
| TC-05 | FR-002、FR-005 | 库存1请求2失败，不创建订单；同编号请求1成功。 |
| TC-06 | FR-002、FR-007 | 有效但不存在的商品、订单编号返回对应 NOT_FOUND 错误；不创建任何记录。 |
| TC-07 | FR-005 | 在 RESERVED、CONFIRMED、CANCELLED 三种状态分别重复原参数预占，返回当前状态，库存不变。 |
| TC-08 | FR-005、FR-011 | 已有订单改数量，或改成不存在的商品，均返回 ORDER_CONFLICT；数量非法时优先返回 INVALID_ARGUMENT。 |
| TC-09 | FR-006 | 确认成功后重复确认10次，或取消成功后重复取消10次，均成功且库存不变。 |
| TC-10 | FR-003、FR-004 | 确认后取消、取消后确认均返回 STATE_CONFLICT；原终态及库存保持不变。 |
| TC-11 | FR-008 | 编号长度1和32通过；长度0和33、空格、中文、斜杠、非字符串均返回 INVALID_ARGUMENT；大小写编号独立。 |
| TC-12 | FR-008 | 初始库存-1或10001非法；预占0、-1或10001非法；布尔值、浮点数、数字字符串、None均非法。 |
| TC-13 | FR-002 | 库存1预占1成功，随后其他订单预占1失败；库存0预占1失败，不产生负数。 |
| TC-14 | FR-010 | 修改 create_sku、reserve、confirm、cancel、get_sku、get_order 返回的 data 后重新查询，内部结果不受影响。 |
| TC-15 | FR-010、NFR-001 | 同实例创建两个商品，操作其中之一不影响另一个；两个实例使用相同编号仍相互独立。 |
| TC-16 | FR-009、NFR-002 | 同时释放100个线程，各以不同订单编号预占同商品1件；初始库存10，恰好10个成功、90个 INSUFFICIENT_STOCK，最终0,10,0；全新实例重复5轮。 |
| TC-17 | FR-005、FR-009 | 100个线程使用同一订单及原参数预占1件，全部成功且返回相同订单；初始库存10，最终9,1,0。 |
| TC-18 | FR-009 | 一个已预占订单同时确认和取消，恰好一个成功、另一个 STATE_CONFLICT；库存与最终状态一致，不接受双成功。 |
| TC-19 | FR-009、FR-011 | 并发写入时穿插查询，每个返回快照都满足守恒且非负；业务失败的请求没有造成部分更新。 |
| TC-20 | FR-007、FR-011、NFR-001、NFR-002 | 检查六个公开方法、结果结构和字段；按说明在无第三方依赖的环境运行 unittest，记录实际执行数及失败详情。 |

并发用例使用同步屏障或事件同时放行工作线程，不通过仅顺序调用或固定 sleep 代替竞争；必须等待全部线程结束，并为等待设置合理超时。不限定具体哪个订单抢占成功。并发取样检查中，每份商品快照本身必须一致；不同时间取得的两份快照不要求相等。失败无副作用指该请求自身不修改状态；仅在没有其他并发写入时比较其前后快照。

## 八 在 SWE-Olympus 中使用

在项目中心选择本目录的 `requirement.json`。预检应显示13条需求、编号唯一、正文指纹一致、确认目标匹配，来源状态为“构造样例”；保存后可阅读条目和原文。选择本 Markdown 文件时会按“待整理材料”展示，适合人工阅读，结构化导入应使用 JSON。

服务端测试接纳须显式启用 `RequirementBridge(allow_synthetic=True)`。配套确认只供测试，正式环境仍须提供受信来源及真实确认记录。现有网页的设计生成入口尚未接通；该文件可验证导入，后续设计、规划和执行需由宿主服务接线。

这是区别于内置校园样例的新业务。Athena、Daedalus 等模型步骤需要配置实际 provider，或提供与本需求版本和指纹匹配的测试响应；不能沿用校园案例的默认 Mock 输出。需求文件本身不会自动注册任务或创建 P6 运行记录。
