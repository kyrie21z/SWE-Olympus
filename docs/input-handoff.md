# 需求文件交接

本入口承接上一阶段的需求规格，业务主题不限。目标流程是：**REQ文件 → 正式接纳 → 设计规格DS → 任务计划PLAN → 审查与真人确认 → 编排执行 → 验收**。P1只实现本地导入、预检、预览和保存；后续流程展示为空状态。

## 1. 用户怎样导入

1. 从上一阶段导出REQ JSON，在欢迎页选择或拖入文件。
2. 查看需求条目、验收条件、范围外限制、来源、版本、指纹和确认记录。
3. 根据预检提示修正文件；项目名称和补充说明独立保存，不修改规格原文。
4. 保存导入记录并进入工作台，继续查看原文或导出原文件。正式生成按钮在后续服务接入前禁用。

| 文件 | 本期行为 |
| --- | --- |
| `.json` | 按公共Requirement契约预检，失败不保存；通过只允许本地预览 |
| `.md`、`.txt` | UTF-8原文预览，标为待整理材料，需在上游形成有效REQ |
| PDF、Word及其他 | 明确拒绝，解析尚未接入，不能只改扩展名导入 |

限制：单文件512 KB，20份记录，总原文2 MB；二进制、空文件、无效UTF-8拒绝。原文按文本显示，不执行其中的HTML或指令。不上传文件、不调用模型。

## 2. 正式JSON长什么样

以现有[Requirement Schema](contracts/schema.json)为准，查看或下载[完整格式样例](../frontend/public/examples/requirement.json)。样例由Python生成，使用团队文档检索场景，只说明格式，界面不会自动载入它。

| 字段 | 内容 |
| --- | --- |
| `schema_version`、`kind` | 当前契约`1.0`、对象类型`REQ` |
| `object_id`、`version`、`content_hash` | 需求标识、正整数版本、正文的SHA-256指纹 |
| `content.requirements` | 每条包含唯一`id`、`text`与`acceptance` |
| `content.out_of_scope` | 明确不做的范围 |
| `provenance` | 来源类别、来源标识与定位信息 |
| `confirmation` | 可为空；非空时含确认人、时间、来源、精确目标与依赖引用 |

从上游服务导出真实文件时使用Python契约和`fingerprint`，不能编辑样例正文后沿用旧指纹或确认。Design（`kind=DS`）不能放进REQ入口。

## 3. 预检结果代表什么

| 状态 | 含义 |
| --- | --- |
| 校验未通过 | 格式、字段、重复编号、正文指纹或确认目标不匹配，不允许保存 |
| 待整理材料 | MD/TXT尚未形成结构化REQ |
| 待补充确认 | REQ结构有效，但没有确认记录 |
| 构造样例 | 任一来源或确认标为synthetic_fixture，仅供演示 |
| 待服务端核验 | 本地检查通过且携带确认声明，仍需核验其真实性与权限 |

浏览器只比较内容和引用，不认证文件作者。即使把origin写成human，也不会显示“正式已确认”。`canSave`只控制本地保存，不能启动Design生成。重新打开记录时重算报告，不持久化或信任“通过”标记。

后续P4服务必须独立校验所有字段、授权、依赖有效性及真实确认；P3对计划批准和执行命令负责。导入成功不能替代这些关口。

## 4. 保存、版本和失败处理

- 本地记录存于`olympus.requirement-imports.v1`，与正式REQ/DS/Run分开。更换规格产生另一份导入记录；P1不推断哪个业务版本是当前批准版本。
- 文件名、原文及编码内容保留，补充说明不合并进需求。导出原文件不附加说明或确认。刷新后恢复，并重新预检。
- 损坏、未知存储版本、容量不足均提示错误，不用空列表覆盖原数据。保存前检测其他页面改动；这是本地冲突提示，不提供跨标签页事务。
- 快速更换文件时，仅接纳最新读取/校验结果，旧异步结果不覆盖新选择。
- 旧`olympus.prompt-drafts.v1`保留原样，页面提供导出入口；不删除、不自动转换为REQ。
- 正式上传、文件解析服务、去重版本登记及多用户并发由后续服务实现。
